# Безопасность

Для сообщения об уязвимости используйте **Security → Report a vulnerability**
в [репозитории Work Board](https://github.com/greedval-us/work-board/security/advisories/new),
если закрытая отправка включена. Если кнопка недоступна, запросите у владельца
закрытый канал связи через issue без описания уязвимости.

В закрытом сообщении укажите версию приложения, среду, минимальный сценарий,
влияние и способ воспроизведения на искусственных данных.
Не отправляйте рабочие базы, персональные данные, ключи или неочищенные журналы в публичные issue.

Основные границы проверки: доверие к источнику IPC, безопасные публичные ошибки,
доступ renderer к файлам и Node.js, выбор и миграции SQLite, изоляция поколений базы
и содержимое Excel. Исправления готовятся для актуального состояния репозитория;
отдельный график поддержки старых версий пока не установлен.

## Проверка зависимостей

Корневой lockfile фиксирует зависимости приложения и сборщика. Отдельный lockfile в
`packaging/legacy` фиксирует библиотеки, которые входят в 32-разрядную сборку для старых версий Windows.
Оба Windows workflow запускают `npm run check:dependencies` для полного аудита обоих деревьев.
Чтобы получить отчёты в JSON и отдельно проверить зависимости приложения, выполните четыре команды из корня репозитория.

```sh
npm audit --json
npm audit --omit=dev --json
npm --prefix packaging/legacy audit --json
npm --prefix packaging/legacy audit --omit=dev --json
```

23 ноября 2026 года все четыре команды завершились с кодом 0. В каждом отчёте npm число известных предупреждений было равно нулю. Проверка выполнена с Node.js 24.15.0 и npm 11.12.1 через публичный реестр npm. При изменении зависимостей или перед выпуском повторите команды, поскольку база предупреждений обновляется.

Современная x64-сборка включает Electron `45.4.1`. В корневом проекте пакет `electron` и сборщик `electron-builder` версии `26.18.0` находятся в `devDependencies`, поэтому для их проверки нужен полный аудит. [График поддержки Electron](https://releases.electronjs.org/schedule).

Два ограничения версий требуют внимания при следующем обновлении библиотек.

- В обоих профилях ExcelJS `4.4.0` использует `uuid` версии `11.1.1`. Эта версия содержит исправление и предоставляет CommonJS-функцию `v4()`, с помощью которой ExcelJS записывает идентификаторы условного форматирования в XLSX. [Предупреждение uuid](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq).
- В корневом дереве сборщика диапазон `minimatch@>=7 <11.0.1` заменён на `11.0.1`. Зависимости, использующие прежний API веток 3 и 5, сохраняют свои версии. После изменения этого ограничения проверьте состав ASAR и запустите проверки обоих Windows-пакетов. [Предупреждение minimatch](https://github.com/advisories/GHSA-g3hv-75wg-m249).

Для Windows 7 SP1 / 8 / 8.1 / 10 x86 упаковщик отдельно загружает Electron `22.3.27` и нативный модуль SQLite для его ABI. Аудит legacy lockfile охватывает npm-пакеты, в том числе `better-sqlite3`. Скачанные бинарные файлы и встроенный Chromium находятся за пределами этой проверки. Поддержка Electron 22 завершилась в октябре 2023 года. Этот профиль сохраняется для совместимости и использует движок без текущих исправлений безопасности. [Объявление Electron о поддержке старых версий Windows](https://www.electronjs.org/blog/windows-7-to-8-1-deprecation-notice).

## Артефакты и публикация

Workflow **Build Windows artifacts** вызывает сборку с `--publish never` и сохраняет
неподписанные проверочные артефакты в GitHub Actions. Перед публичным выпуском
проверьте подпись исполняемых файлов, результаты проверок пакетов и актуальный аудит зависимостей.

# Участие в разработке

Используйте Node.js из `.nvmrc` и npm. После клонирования:

```sh
npm ci
npm run dev
```

Согласуйте существенное изменение в issue, затем подготовьте отдельную ветку и PR.
Описание PR должно объяснять результат для пользователя и содержать команды проверки.
Скриншоты интерфейса делайте на тестовых данных; рабочие SQLite, XLSX и секреты в репозиторий не добавляются.

## Границы кода

- Main services собирают операции, repositories выполняют параметризованный SQL.
  Новая схема добавляется последовательной миграцией с сохранением старых данных.
- Renderer services вызывают только именованные методы через `requestDesktop`.
  Pinia stores владеют данными и запросами, composables — состоянием карточек и жизненным циклом UI.
- В компонентах используйте Composition API, props/emits и `storeToRefs` для состояния Pinia.
  Не переносите SQL, файловый доступ или произвольный IPC в renderer.
- Для новых запросов сохраняйте generation, revision и защиту устаревших ответов.
  Ошибки для пользователя должны проходить через общий безопасный контракт.

Подробности: [архитектура](docs/architecture.md).

## Проверки

```sh
npm run check
npm run test:desktop
```

Для изменений иконки обновите `src/public/icons/app.svg` и выполните `npm run icons`.
Для упаковки Windows:

```sh
npm run build:win -- --publish never
npm run test:package
```

Добавляйте тест для изменяемого поведения: фильтров, хранения, ошибок, гонок или пользовательского сценария.
В PR укажите ограничения ручной проверки. Workflow сборки запускается вручную и сохраняет artifacts;
создание релиза выполняется отдельным решением владельца репозитория.

# Архитектура Work Board

Приложение разделено на main, ограниченный preload, Vue renderer и shared.
Реестр указаний, календарь и самостоятельные задачи используют выбранную локальную SQLite.
HTTP/gRPC-сервера и сетевой базы нет.

## Main

`createApplicationServices.js` собирает database, repositories, services и IPC-зависимости.
Зависимости передаются явно: сервисы вложений и аналитики не создают свои репозитории.
`index.js` отвечает за bootstrap и lifecycle: восстанавливает выбранную базу,
регистрирует IPC и создаёт окно. Отсутствие базы не мешает запуску интерфейса:
пользователь выбирает файл в настройках.
`app.js` отвечает только за BrowserWindow и загрузку UI.

`DatabaseService` владеет активным соединением и его поколением (`generation`).
Проверка кандидата только для чтения вынесена в `inspectDatabase`, подготовка файла,
подключения и PRAGMA — в `prepareConnection`. Идентификатор базы, timeout и требуемые
столбцы собраны в `databaseConfig`. Миграции и операции сохранения используют один
`runTransaction`; `DatabaseService.transaction` принимает только синхронную операцию.
Если откат или очистка отклонённого соединения также завершается ошибкой,
`CleanupError` сохраняет исходную причину в `cause` и все ошибки в `errors`.
Очистка остальных ресурсов продолжается; существующий файл базы не удаляется.
`DatabaseLocation` сохраняет путь в `userData/database-location.json` и восстанавливает его
при запуске. Если конфигурации ещё нет, распознаётся база прежней установки
`userData/data/work-board.sqlite`; она остаётся на прежнем месте.
Отсутствующий выбранный файл не создаётся заново автоматически.

`DatabaseSelectionService` открывает отдельные системные диалоги создания и открытия
и не допускает одновременных выборов. Создание использует эксклюзивное открытие файла
и отказывается перезаписывать существующий. Кандидат на открытие сначала проверяется
только для чтения: принадлежность Work Board, версия, структура и целостность.
Чужие и более новые базы отклоняются до включения WAL и изменяющих PRAGMA.
После подготовки кандидата сохраняется путь, затем меняется активное соединение.
Отмена диалога или ошибка сохраняет прежнюю активную базу.

`migrations.js` применяет версии транзакционно через `PRAGMA user_version`.
Схема 6 добавляет `control_schedule` в `instructions`. График и отметки хранятся вместе
с указанием. Для прежних записей график пуст. Варианты списков реестра хранятся в `app_settings` выбранной базы.
Соединение использует WAL, foreign keys и busy timeout и закрывается при выходе.

Repository содержит подготовленные SQL-запросы; service описывает операции;
handler переводит операции в именованные IPC-методы. `RecordService` связывает
чтение репозитория и политику записи вложений для одного типа записи. IPC не выбирает
между прямым сохранением репозитория и сохранением через вложения. Для новых сущностей
используйте тот же подход. Не добавляйте бизнес-логику в IPCManager.
`electron-log` пишет ошибки main в стандартную папку журналов приложения.

## Предметные данные и экспорт

`InstructionRepository` выполняет CRUD указаний, постраничную выборку и выборку всех
подходящих строк для выгрузки. У указания есть исходный срок и необязательная дата продления,
статус `pending`, `in_progress` или `completed` и текстовый комментарий.
Номера остаются строками и могут повторяться. Фильтры объединяются через И:
номер, включительный интервал сроков, исполнитель, статус и текст отметки.
Нормализованные поисковые поля поддерживают русский регистр и буквальный поиск `%`/`_`.
SQL параметризован, сортировка ограничена допустимыми полями и имеет стабильный порядок.

`TaskRepository` хранит самостоятельные задачи с датой, описанием, приоритетом
`normal`, `important` или `urgent` и признаком выполнения.
`CalendarService` читает оба репозитория и рассчитывает промежуточные даты в пределах запрошенного периода.
Календарь раздельно показывает итоговые сроки, промежуточные даты и самостоятельные задачи.
Промежуточные даты рассчитываются до действующего срока указания, а сохранённые отметки доступны и после изменения графика.
Необязательный `controlSchedule.moves` хранит переносы `{ from, to }` отдельных дат,
не изменяя исходную периодичность. Общие функции применяют переносы при расчёте календаря,
ближайшей даты и фильтров просрочки, включая перенос между месяцами. Пересечение дат
отклоняется до изменения черновика. Отметка хранит плановую `date` и необязательную
фактическую `actualDate`; у прежних отметок фактической считается `date`.
Фактическая дата не ограничена периодом планового контроля. Экспорт Ф‑21 сортирует
историю по фактической дате. Поля сохраняются в существующем JSON без миграции схемы.
Фильтры реестра на календарь не влияют. Изменения срока, статуса и удаление
отражаются в календаре после общего обновления данных.

Календарные даты хранятся как `YYYY-MM-DD` без преобразования через UTC;
технические timestamps создания и изменения отделены от них.
Общие проверки значений находятся в `shared/validation.js`, календарные даты —
в `shared/dates.js`, доменные статусы, приоритеты, поля и параметры страниц —
в `shared/constants/`. `shared/registry.js` сохраняет общий публичный вход.
Версионированные SQL-миграции сохраняют исторические литералы, чтобы будущая смена
констант не меняла уже выпущенную схему.

`ExcelExportService` проверяет поколение и делает снимок всех подходящих строк
до асинхронного диалога сохранения. `RegistryWorkbook` создаёт ExcelJS-книгу:
лист «Указания» содержит тринадцать столбцов с полным текстом в заданной сортировке,
лист «Параметры» — фильтры, период, сортировку, время выгрузки и число строк.
Строки не интерпретируются как формулы; начальные нули номеров сохраняются.
Экспорт записывается через временный файл. Отмена диалога возвращает `cancelled`,
а не ошибку.
`files/atomicFile.js` объединяет запись XLSX/DOCX и скачивание вложений:
создаёт собственный временный файл, записывает содержимое и заменяет назначение
только после успешной подготовки. Общая проверка запрещает перезапись рабочей
базы, её WAL/SHM и папки вложений, включая пути через ссылки. Для Word и скачивания
поколение проверяется непосредственно перед синхронным переименованием.
Ошибка удаления временного файла сохраняется вместе с исходной ошибкой операции.

## Вложения и аналитика

`AttachmentService` координирует обе сущности, `AttachmentRepository` хранит метаданные
с foreign keys и каскадным удалением. Каждое вложение принадлежит ровно одной задаче
или указанию. Файлы находятся в `<полный путь SQLite>.files/{tasks|instructions}/{id}/`;
в базе сохраняются только исходное имя, относительный путь, размер и дата добавления.
Внутренние уникальные имена предотвращают коллизии исходных имён.
`AttachmentSelections` владеет токенами выбора, их принадлежностью и лимитами.
`AttachmentStorage` владеет файловыми путями, проверками безопасности, копированием
и очисткой; отдельный batch владеет временными файлами одного сохранения.
Лимиты и имена папок определены в `shared/constants/attachments.js`.

`attachments.pick` открывает системный диалог и выдаёт непрозрачные токены,
привязанные к типу записи и поколению базы. Renderer не выбирает исходные пути.
Изменения карточки несут `data.attachments = { add: [{ token }], remove: [id] }`.
Renderer формирует обычные объекты, поскольку Vue proxies не копируются через IPC.
До сохранения изменения существуют только в форме и списке токенов main.
`attachments.release` освобождает токены при отмене формы или снятии нового вложения.

При сохранении копирование асинхронно создаёт временные файлы `.staging` рядом с базой.
Затем короткая синхронная транзакция сохраняет владельца и метаданные, перемещая
копии в его папку. Ошибка откатывает SQLite и удаляет новые копии; токены остаются
для повторной попытки. Удалённые файлы очищаются после commit. Сбой очистки
записывается в main-журнал. Скачивание по ID вложения и владельца создаёт временную
копию в выбранном месте и переименовывает её после проверки поколения.
Пути проверяются на выход за папку, junction/symlink и перезапись рабочей SQLite.
После асинхронных границ проверяется поколение; renderer блокирует переключение
базы через `withOperation` на время выбора, сохранения и скачивания файлов.
Обновление перечитывает строку и объединяет частичные изменения внутри транзакции:
асинхронное копирование не затирает параллельно изменённые поля карточки.

`AnalyticsRepository` группирует указания по исполнителю, статусу и месяцу действующего срока.
Запрос охватывает всю выборку реестра. `AnalyticsSummary` рассчитывает общие показатели,
помесячные значения и сводку по исполнителям. Фильтры ограничивают выборку по исполнителю,
статусу и включительному периоду. Выбор исполнителя использует точный ключ и добавляет
постраничный список его указаний. Графики показывают текущие статусы по срокам. `analyticsStore`
хранит применённые и черновые фильтры, защищает ответы поколением и revision,
сохраняет выбор при переходах и обновляется после изменений данных.
`Analytics.vue` компонует отдельные фильтры, показатели и графики с числовыми
подписями и существующими CSS-токенами светлой и тёмной тем.
Правила изменения фильтров, периодов, черновиков и снимков находятся в renderer/domain;
подписи, цвета приоритетов, размеры файлов и представление календарных строк —
в renderer/presentation. Компоненты отвечают за отображение и события, stores —
за состояние и операции. Повторяющиеся desktop adapters создаются фабрикой с явным
списком разрешённых namespace/method; универсальный IPC не публикуется.

## Настройки и служебные сценарии

Параметры окна и книги Excel находятся в `main/config`, параметры разработки
в `shared/constants/runtime.js` используются Vite, main и проверкой dev-режима.
В `scripts/lib` выделены окружение и запуск процессов, безопасная временная папка,
драйвер Electron smoke и кодирование форматов иконок. Сценарий `registrySmoke`
содержит проверяемые пользовательские действия, а не реализацию DOM-драйвера.
Таймауты и геометрические допуски имеют имена в своей области применения.

## Preload и shared

Preload собирается Vite в `build/main/preload.cjs`.
`contextBridge` публикует только `window.desktopAPI`:

```js
desktopAPI.app.getInfo()
desktopAPI.database.getStatus()
desktopAPI.database.create()
desktopAPI.database.open()
desktopAPI.settings.get(generation)
desktopAPI.settings.setTheme('dark', generation)
desktopAPI.instructions.list({ filters, sort, offset, limit, generation })
desktopAPI.instructions.get({ id, generation })
desktopAPI.instructions.create({ data, generation })
desktopAPI.instructions.update({ id, data, generation })
desktopAPI.instructions.remove({ id, generation })
desktopAPI.instructions.export({ filters, sort, generation })
desktopAPI.tasks.list({ from, to, generation })
desktopAPI.calendar.month({ month, generation })
desktopAPI.calendar.day({ date, generation })
desktopAPI.attachments.list({ entityType, entityId, generation })
desktopAPI.attachments.pick({ entityType, generation })
desktopAPI.attachments.release({ entityType, tokens, generation })
desktopAPI.attachments.download({ entityType, entityId, id, generation })
desktopAPI.analytics.summary({ filters, page, generation })
```

У `tasks` также есть именованные `get`, `create`, `update` и `remove`
с тем же форматом `id`/`data`/`generation`.

Внешняя граница preload возвращает Result envelope:

```js
{ ok: true, value }
{ ok: false, error: { code, message } }
```

`registerIpcHandlers` выполняет проверку источника, вызывает именованную операцию
и переводит ожидаемые и технические отказы через `publicError`.
Подробная причина остаётся в локальном журнале main.
`requestDesktop` в `renderer/infrastructure/desktopApi.js` проверяет форму ответа
и декодирует его в обычное значение либо доверенный `DesktopError`.
Renderer services не дублируют разбор envelope; stores работают с результатом или исключением.
Неожиданная ошибка транспорта превращается в безопасное сообщение без внутренних данных.

`shared` не импортирует Electron, DOM, SQLite или Node.js.
Здесь хранятся имена каналов и общие правила значений.
Нельзя публиковать `ipcRenderer.invoke`, SQL или универсальный файловый доступ.
IPC принимает запросы только из главного frame текущего окна.
Параметры и поколение проверяются в main до обращения к данным.
Renderer не передаёт произвольные файловые пути: выбор SQLite и места XLSX
выполняют main services через системные диалоги.

## Renderer

Компоненты описывают интерфейс, передают props вниз и emit вверх.
Views собирают компоненты; layout содержит оболочку.
Setup Pinia stores `registryStore` и `calendarStore` владеют предметными данными,
снимками запросов, состояниями загрузки, ошибками операций и действиями CRUD/экспорта.
Они сохраняют данные при смене маршрута. Компоненты используют `storeToRefs`
при извлечении состояния; данные не копируются в локальные refs.
Renderer services адаптируют bridge через `requestDesktop`.
Тонкие composables управляют выбранной карточкой, черновиком формы, guards
и поведением жизненного цикла Vue.
`controlCardStore` нормализует снимок полей отчёта Ф‑21, выполняет экспорт
через `withOperation` и хранит состояние запроса и безопасные уведомления.
`ControlCardDialog` хранит только редактируемые поля, значения по умолчанию
и состояние диалога; закрытие формы сбрасывает уведомления, но не снимает
защиту ещё выполняющегося экспорта.
`useAttachmentDraft` привязывает запросы и выбранные токены к снимку владельца
и поколения базы. Поздний выбор после закрытия или смены карточки освобождается
с исходным контекстом, а его результат и ошибка не попадают в новый черновик.
Отсутствие Electron API отображается как ошибка; браузерного mock-хранилища нет.
Тема меняется после успешного сохранения в выбранной SQLite.

`Registry.vue` и `Calendar.vue` собирают компоненты своих разделов.
`registryStore` хранит отдельные черновые и применённые фильтры; запрос списка
и экспорт получают только применённый снимок. `useRegistry` хранит локальный выбор карточки
и её исходное поколение. Таблица имеет собственную прокрутку,
закреплённые заголовки и страницы по 25/50/100 строк.
Реестр и календарь заполняют доступную высоту через flex/grid с `min-height: 0`;
общая страница не прокручивается. Фильтры находятся в native popover в верхнем слое,
их черновик сохраняется при закрытии. Столбцы таблицы по умолчанию делят доступную ширину;
увеличение ширины с внутренней горизонтальной прокруткой включается явно.
Календарь делит остаток высоты на пять или шесть недель; у указаний и задач дня
независимые области прокрутки. Компактная навигация раскрывается поверх интерфейса,
временно делает основной контент `inert` и удерживает фокус внутри меню.
Общие длительности и кривые находятся в `styles/motion.css`. Страницы используют
Vue Transition, фильтры — native popover с дискретными переходами `display`/`overlay`.
`infrastructure/dialogMotion.js` управляет native dialog: начинает открытие сразу,
перед закрытием дожидается визуального выхода, отменяет прежний эффект при новом
действии и защищает запоздавшее завершение версией операции. У реестра отдельное
состояние присутствия карточки сохраняет её до конца выхода, не меняя бизнес-выбор.
Контроллеры снимают обработчик системного режима уменьшения движения при unmount.
Карточка указания и форма задачи используют native dialog, явные сохранение и отмену,
подтверждение удаления и сохраняют ввод при ошибке.
Календарь начинает неделю с понедельника, обновляет срочность в полночь и при фокусе окна;
указание открывается из дня через маршрут `/?instruction=<id>`.

`appStore` хранит статус базы, общий `revision`, число `pendingOperations`
и признак выбора базы. Запись и экспорт выполняются через `withOperation`;
на время операции переключение и закрытие блокируются.
Успех изменения увеличивает `revision`, после чего разделы обновляют данные.

Несохранённые формы регистрируют асинхронные guards. Переход, выбор базы
и закрытие окна предлагают сохранить, отбросить изменения или продолжить редактирование.
Main обрабатывает `will-prevent-unload` и повторяет закрытие только после разрешения renderer.
Карточка хранит поколение, в котором была открыта; при смене базы она закрывается.
Проверки поколения и последовательности запросов не дают устаревшим ответам
заменить новый список или отправить старый ID в другую базу.

`requestScope` выдаёт токен актуального запроса и инвалидирует его при новом запросе,
смене контекста или dispose. `createSingleFlight` объединяет одинаковые pending-запросы;
кэш успешных данных принадлежит store. Ключ включает generation, revision и снимок query.
Новый revision после мутации исключает повторное использование старого чтения.
Запоздавшее завершение не снимает состояние загрузки более нового запроса.

## Ошибки и восстановление

Ожидаемые ошибки операции остаются рядом с формой или списком, не очищая ввод.
`errorMessage` показывает только доверенные публичные сообщения `DesktopError`/`ValidationError`;
для произвольной ошибки используется безопасный fallback.
Main преобразует `CleanupError` по исходной причине: вторичный сбой очистки
не заменяет код ошибки операции. Полная диагностика остаётся в журнале IPC,
а произвольные `Error.cause` не считаются доверенным публичным контрактом.
`installErrorHandling` собирает Vue errors, `window.error` и `unhandledrejection`
в единый `errorStore`. Store удерживает одно пользовательское уведомление,
а не историю сырых исключений.
`ErrorBoundary` изолирует сбой раздела и предлагает повторить рендер;
оболочка и навигация сохраняют возможность восстановления.

## Напоминания о сроках

`NotificationService` объединяет сроки указаний, задач и неотмеченные промежуточные даты
через `buildDeadlineNotifications`. Горизонт — локальная текущая дата плюс три календарных дня,
включая всю просрочку. Для указаний используется действующий срок с продлением,
для контрольных дат — существующая модель переносов. Завершённые записи исключаются.
`NotificationStateRepository` хранит независимые подтверждения прочтения и показа
в ключе `notifications.receipts.v1` существующей таблицы `app_settings`.
Идентичность включает тип, ID, время создания записи и исходную дату проверки;
occurrence содержит действующий срок и локальный день. При подтверждении устаревшие
occurrence игнорируются, сохранённые подтверждения объединяются транзакционно,
исчезнувшие сроки очищаются. Данные из другой базы не используются.

Именованные `notifications.list` и `notifications.acknowledge` проходят общий generation/sender guard.
`notificationsStore` сериализует записи, объединяет одновременные чтения и проверяет билет
каждого чтения после ожидания ответа. Старый ответ не может восстановить непрочитанное
состояние после подтверждения или смены базы. `useNotifications` управляет таймером
на минуту/полночь и обновлением при возвращении в окно; скрытое окно и открытая модальная
карточка откладывают новый popup. Ошибка сохранения не повторяет popup в этой сессии,
но оставляет безопасную ошибку и повторяет запись при следующем обновлении.

Один `NotificationCenter` в общей шапке показывает счётчик, группы сроков с порционной
загрузкой строк и агрегированную всплывашку. Прочтение и закрытие всплывашки разделены.
Переходы используют токен для повторного открытия той же записи, защищают несохранённые
формы и устаревшие ответы при открытии задачи.

На Windows `NativeNotificationScheduler` в main проверяет сроки каждую минуту,
при resume/unlock и после успешных изменений записей или выбора базы. Он продолжает работать
при скрытом renderer. Платформенный `Notification` внедряется через composition root.
Pending occurrences объединяются в один toast, подтверждение popup сохраняется после события
`show` (Windows приняла уведомление; пользовательские настройки ОС всё ещё могут скрыть баннер).
Ошибки и отсутствие `show` дают не более трёх попыток за сеанс для occurrence.
Сбой записи receipt повторяет запись без нового toast. Объекты уведомлений удерживаются
для обработки click после скрытия баннера, с ограничением количества и очисткой при смене
дня/базы, исчезновении срока и завершении приложения.

Snapshot уведомлений содержит `delivery` с режимом и безопасной ошибкой: системный режим
подавляет дублирующие всплывашки renderer. Ошибки доставки отличаются от ошибок проверки/сохранения.
Click проверяет generation/day/occurrence, восстанавливает окно и отправляет только generation
через отдельное событие preload `notifications.onOpen`; Electron event не передаётся.
Запрос открыть колокольчик пережидает начальную загрузку базы и закрытие модальной карточки.

`WindowLifecycle` отделяет закрытие окна в трей от полного выхода. Скрытие сохраняет черновики,
а явный выход использует прежний renderer guard и при необходимости возвращает окно на экран.
Если трей не создался, обычное закрытие продолжает завершать приложение. Bootstrap вынесен
в `startDesktopApplication`, ресурсы трея/планировщика/IPC/SQLite освобождаются при завершении.
`windowsIdentity` устанавливает AppUserModelID, совпадающий с NSIS appId и ярлыком «Пуск»;
portable/dev не выполняют автоматическую регистрацию ярлыка. Автозапуск Windows не изменяется.

## Сборка и ресурсы

`vite.config.js`: renderer → `build/renderer`; относительные URL и hash router.
`vite.preload.config.js`: preload → `build/main/preload.cjs`.
Main остаётся ESM и включается в ASAR вместе с необходимыми shared-модулями.
В пакет не включаются tests, docs и scripts. База лежит вне ASAR и папки установки.
`src/public` копируется Vite в renderer; там можно разместить иконки и ресурсы.
Исходная иконка находится в `src/public/icons/app.svg`; `npm run icons` создаёт PNG/ICO.
`app-256.png` используется в README. `npm run test:package` проверяет готовый Windows-пакет
после `npm run build:win`; отдельный ручной workflow сохраняет artifacts без публикации релиза.

## Проверка

`npm test` запускает существующие тесты в `tests/main`, `tests/shared` и `tests/renderer`:
реальную SQLite во временных папках, миграции, CRUD, Unicode и буквальные фильтры,
границы дат, сортировку и страницы, календарные агрегации, выбор и отказ открытия баз,
XLSX с чтением результата, ограниченный bridge/IPC и состояние renderer при гонках и ошибках.
Тесты Pinia проверяют сохранение состояния между маршрутами, single-flight,
порядок запросов и обновление после мутаций. Тесты error infrastructure проверяют
публичный контракт ошибок и обработку неожиданных сбоев.

`npm run test:desktop` собирает клиент и запускает `scripts/registrySmoke.mjs`
через `scripts/checkDesktop.mjs`. Сценарий использует реальный bootstrap, preload и Vue,
изолированную userData и заданные ответы системных диалогов. Он содержит проверки
первого запуска, выбора баз, CRUD через формы, фильтров, XLSX нескольких страниц,
счётчиков календаря, задач, отказа записи при блокировке SQLite, несохранённой формы,
тем, компактного окна и изоляции Node.js. Скриншоты сохраняются в `output/`.
Вариант `npm run test:desktop -- --dev` использует временный Vite-сервер.
На Windows дополнительно запускается `backgroundSmoke.mjs`: настоящий Electron, трей и SQLite
с проверкой minimize/close/hide/restore, фонового чтения после внешнего изменения базы,
перехода из системного уведомления, сохранения черновика и явного выхода. Native Notification
заменён тестовым адаптером, чтобы не отправлять тестовые сроки на рабочий стол пользователя.
Фактическая доставка баннера ОС и регистрация установленного пакета требуют отдельной проверки
в установленной NSIS-версии с разрешёнными уведомлениями Windows.
